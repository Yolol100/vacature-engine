# Vacature Radar technische hulpmiddelen (historisch)

**Status 2026-10-18:** De GitHub Actions Radar-, uurlijkse bewijs- en vieruurs-observatieworkflows zijn verwijderd op verzoek van de gebruiker. Het onderstaande beschrijft alleen historische bediening en technische code; er is geen actieve automatische of handmatige GitHub-radaruitvoering. Nieuwe vacatures worden uitsluitend op expliciete ChatGPT-opdracht via de live Register-bronnen gezocht.

Independent read-only technical review using the 13 official ATS tenants from `ingestion/source-specs.radar.json`.

- Entry point: `.github/workflows/vacature-radar.yml`
- Node CLI: `radar/src/actions-review-cli.mjs`
- State restoration: `radar/scripts/load-review-state.sh`
- Durable checkpoint: `radar/scripts/persist-review-state.sh` on existing `radar-state` branch
- Checkpoint requires manual `workflow_dispatch` by repository owner, `persist_review=true`, and `RADAR_PERSIST_APPROVED=yes`.
- No automated application, email or unattended technical-state writes. The scheduled GitHub ATS reader now appends **only** official ATS observations with a confirmed publication timestamp no older than 7 days and a WordPress/automation title family to the already-owned private `Vacature Radar - Nieuwe Vacatures` Google Sheet, deduping again against live submitted applications. It does **not** write to the canonical `Vacature Register` or claim these candidates are already fully verified/remote-from-NL eligible. Unknown or older publication dates remain unlisted, and official employer/ATS, language, NL and fit checks are performed again by the ChatGPT consumer. The scheduled job still covers only 13 official ATS tenants; the wider active source registry and web-only sources require separate safe discovery lanes. No sending or application submission. The existing observation workflow `.github/workflows/vacature-quarter-hour.yml` retains its historical filename and workflow name for consumer compatibility, but now runs **once every four UTC hours at :17** (`17 */4 * * *`), starting at 00:17 UTC. Its bounded artifacts are read directly by the existing ChatGPT `Vacature Radar` task **every three hours**. The previous `vacature-hourly-evidence.yml` cron has been removed; that workflow remains an owner-gated manual historical diagnostic only and must not be counted as a scheduled deliverable. In each rolling three-hour interval, compute actual four-hour slots (zero or one, depending on the window); only real GitHub `event=schedule` executions with valid artifacts count. GitHub schedules are best-effort and may be delayed or skipped. The task independently verifies official vacancies even when no GitHub event occurs. No new scheduler is introduced; the existing Google Radar technical tabs receive only deduped source-check receipts and unverified discoveries, never canonical application-state writes.
- The existing four-hour GitHub workflow now also attempts **eight approved public API/RSS feeds** via an independent read-only discovery step. It stores a bounded `radar-discovery-<runid>` artifact listing sources checked/failed and up to ten UNVERIFIED leads. Feed-only leads do not enter the private Radar `Nieuwe vacatures` tab until an official employer/ATS role is verified, its date is established, and application history is checked by ChatGPT. Failures in the feed discovery step cannot suppress official ATS result/Drive storage and remain visible as partial evidence. This does NOT mean all 219 registered active sources were automatically searched; ChatGPT still follows the live source policy for web-only employer sites, X-ray searches and jobs boards.
- Node checks: `cd radar && npm run check && npm test`.
- Node and focused Python regression jobs run in parallel in `.github/workflows/vacature-radar.yml` on code changes.
- Python regression: `python -m unittest discover -s ingestion/tests`.

## Optional tiered discovery (read-only)

The original `[radar] review 5` issue command and default manual workflow still review only the 13 validated official ATS tenants. To expand manually, start the existing workflow with `discovery_scope=tiered` and `persist_review=false`, or open an owner-authored issue titled `[radar] discover 5` or `[radar] discover 10`. No schedule is enabled.

The same Sheets baseline, live source statuses, Config `direct_discovery_order` / `high_source_order`, vacancy/application deduplication and ATS checks run first. When the preliminary review queue is not full, the existing deploy manifest supplies up to eight read-only public API/RSS sources: Jobicy, Remotive, Himalayas, Remote Landers, RemoteJobs.org, Arbeitnow, We Work Remotely and Remote OK, ordered by live Register policy. Inactive/retired sources are skipped, unavailable providers become explicit errors, and further feeds stop when the limited **manual lead queue** is full. Untested web-only boards are **not** advertised as automated. The scheduled workflow keeps the official ATS intake separate from the new approved eight-feed read-only discovery. The manual review workflow still permits broader owner-only discovery without persistence. The optional `discovery.manual_fallback_sources` contains still-active high-priority web sources (e.g. LinkedIn, Indeed, Google Jobs and The WP World) that require a separate official-role search/verification; these entries have **not** been fetched by Radar.

The extra output is `discovery.candidates` with `discovery_url`, a visible provider attribution link, and `discovery_only` status. These are **not verified or eligible vacancies**: validate the exact employer-owned ATS/careers role, full remote/NL execution, language and fit under Vacature Search before showing or saving. No discovery lead can create a checkpoint receipt, write Google Sheets, apply, send email or turn on an ingestion writer. `persist_review=true` with `discovery_scope=tiered` fails closed. Existing normal ATS checkpoint recovery remains unchanged. For source contracts and attribution respect [Himalayas](https://himalayas.app/docs/remote-jobs-api), [Remotive](https://remotive.com/remote-jobs/api), [Jobicy](https://github.com/Jobicy/remote-jobs-api) and [We Work Remotely](https://weworkremotely.com/remote-job-rss-feed).

## Maximum public-source coverage (manual, read-only)

Run **Actions → Vacature Radar → Run workflow**, choose `discovery_scope=maximum` and leave `persist_review=false`, or open an owner-authored issue titled `[radar] maximum 5` or `[radar] maximum 10`.

Maximum mode reads the same live Register policy, keeps the official ATS review first, then polls **all eight** previously registered public API/RSS connectors on the bounded deployment manifest: Jobicy, Remotive, Himalayas, Remote Landers, RemoteJobs.org, Arbeitnow, We Work Remotely and Remote OK. The public APIs are queried with narrow documented search/category limits and do not receive Google credentials. Maximum mode retains a separate 5/10-item **unverified public lead queue** even when the ATS queue is full, and counts further preliminary matches without claiming eligibility. The default quick `official_only` and opt-in fast `tiered` behavior remain unchanged.

Official ATS tenants now include both ElevenLabs and n8n Ashby company boards. Registered ATS *platforms* without a verified company tenant, web-only boards, directories, employer career pages and third-party searches are reported separately in `discovery.registry_coverage`, not falsely counted as polled. Use the existing Vacature Search live web/X-ray route for prioritized **manual** follow-up, with exact official employer/ATS verification and full Netherlands, remote, language, fit and dedupe gates. A registered source is not a licensed or publicly accessible API.

Do not enable scheduled tiered/maximum public-feed discovery, import applicant data, send email, automatically apply or persist leads from this technical review. The separate scheduled official ATS observation is strictly read-only. Only the original owner-gated `official_only` checkpoint route can write technical receipts. Provider unavailability or HTTP 401/403/429 is a source failure, never silently interpreted as zero roles.

## Registry-wide public surface checks

The same existing GitHub workflow now **attempts every active source registry URL once per four-hour run**, bounded to HTTPS with no redirects, no login, no CAPTCHA bypass, an 8.5-second deadline and at most eight concurrent requests. The `radar-source-sweep-<runid>` artifact gives exact per-source `reachable`, `redirect`, `blocked`, `failed`, or `unsafe` evidence. **A reachable website is NOT a complete vacancy scan** and does not justify new job records. Real vacancy extraction remains limited to the 13 official ATS tenants and eight public feeds. ChatGPT must discover and verify roles on all remaining source classes without overstating coverage. The source-sweep evidence is short-lived and should be recorded into the private `Brondekking` sheet only after validated readback; a missing GitHub schedule is a missing scan, not successful 219-source coverage.

## Single-database scan receipt handoff (2026-10-18)

The EXISTING Google Drive file Vacature Radar - Nieuwe Vacatures is reused. GitHub reads the live Vacature Register > Bronnen, attempts each active public source, and persists only H:K technical evidence in the existing Brondekking tab after source-ID/schema preflight and Google readback. The canonical source registry itself remains read-only. One Runs row is appended per GitHub run, and bounded UNVERIFIED RSS/API and public JobPosting/role-link clues go to the existing Bronvondsten tab after duplicate checks. Employer websites are read only up to 384 KB over HTTPS without redirects or login. Parsed clues are NOT verified roles and job_count remains null. Nieuwe vacatures only receives separately validated official ATS candidates with confirmed recent publication dates.

This is still NOT full vacancy enumeration for all 219 active sources. Dynamically rendered sites, cross-host career systems, unsupported formats, blocked access, missing dates and unrelated roles are explicitly unverified; ChatGPT must verify official roles. No other Drive files or tabs are created. Historical and previously submitted applications remain in the canonical register. Short-lived GitHub artifacts supplement but do not replace durable latest per-source Drive evidence.
